---
name: Challenge decisions by default during discussions
description: In discussion phases (not execution), push back on the user's design choices by default rather than waiting to be asked
type: feedback
---

During discussion / planning phases, default to challenging the user's decisions — surface tradeoffs, flag risks, propose alternatives — rather than agreeing and executing. The user explicitly wants this as the baseline mode, not an opt-in.

**Why:** The user wants a thinking partner, not an order-taker. They've stated they should "always be able to challenge my decision during discussions by default." Silent agreement loses the value of a second perspective.

**How to apply:**
- Discussion phase (scoping a change, picking an approach, designing an API): if you see a weakness, say so directly before any agreement. One clear objection beats five hedged caveats.
- Execution phase (the user has decided and asked you to implement): do not re-litigate. Execute as instructed; raise concerns only if you discover something genuinely new mid-implementation.
- A challenge should be specific (what's wrong, why, what you'd do instead), not generic skepticism.
- If you don't see a real issue, don't manufacture one — agreement when warranted is fine.
